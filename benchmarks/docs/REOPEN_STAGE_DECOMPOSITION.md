# Диагностика повторного открытия Polar.DB

## Зачем

Исторический `ReopenOnly` сообщал `open-only` как «open/close», хотя
`PolarStoreFactory.Open` **конструирует** `USequence` и все четыре внешних
индекса. Их конструкторы могут читать или восстанавливать данные. Поэтому
7,13 с на 5 млн строк нельзя назвать «только открытием дескрипторов файлов».

Сценарий после исправления сохраняет две прежние метрики:
`openSamplesMs` — конструирование всех структур + `Close` (переименовано
по смыслу в constructor-open-only); `samplesMs` — конструирование всех
структур + `Refresh` + проверенный первый primary lookup + `Close`.
Кроме того, появляется `reopenStagesMs` в raw JSON и строки
`metric=reopen/<stage>` в raw CSV. HTML показывает median/p95 стадий.

## Измеряемые этапы

- `raw-file-handles/open-close`: **независимая** проба открытия/закрытия
  существующих `.bin` файлов Polar.DB или файлов SQLite `data.sqlite*`,
  без разбора схемы, восстановления, индексов и запросов. Это не часть
  измеренного engine open и не точное измерение системных `open()` внутри
  движка. Состав и число файлов различаются.
- `constructor-open-only/*`: создание объектов хранилища и закрытие.
  Для Polar.DB: `construct-sequence-and-primary`, `configure-primary-key`,
  `construct-external-0..3`, `close`.
  Для SQLite: `construct-connection`, `open-connection`, `close`.
- `query-ready/*`: тот же конструктор; затем у Polar.DB
  `refresh-flush`, `refresh-metadata`,
  `refresh-sequence-checkpoint`, `refresh-primary`,
  `refresh-external-0..3`, `refresh-try-replay` и, только если
  недействителен checkpoint, `refresh-fallback-rebuild`.
  Далее `first-primary-query-and-oracle`, `close`.
  У SQLite после открытия выполняются первый проверенный запрос и закрытие.
- Порядок индексов `0..3`: Int32, Int64, Guid, String.
  Стадия `construct-sequence-and-primary` включает создание файловых
  потоков и потенциальный recovery scan в конструкторе. Стадии refresh
  включают чтение/материализацию и, если нужно, перестроение.

Измерения берутся из **тех же итераций**, что и общие времена,
с именами стадий и массивами с одинаковыми индексами выборок. Если на разных
измеряемых итерациях выбран разный набор стадий (например, обычный replay
вместо fallback rebuild), сценарий завершается ошибкой, а не смешивает режимы.

Медианы стадий **не аддитивны** и не обязаны давать медиану полного вызова;
расхождение включает мелкие нетаймированные участки и стоимость наблюдателя.
Полный `query-ready` и `constructor-open-only` измеряются в независимых
циклах, поэтому их разность не является причинной стоимостью `Refresh`.
Динамика page cache, GC и JIT не изолируется автоматически.

## Запуск

Из корня репозитория с поддерживаемым SDK:

```bash
dotnet run --project benchmarks/src/ReopenOnly/ReopenOnly.csproj -c Release -- --rows=50000 --warmup=1 --samples=5
```

Полная публикационная серия: повторные независимые запуски с фиксированной
версией продукта, seed, одинаковой конфигурацией индексов, чистым worktree,
отчётами среды и контролем исходных данных. Старые числа
`linux-wsl2-ext4-20261010` сохраняются отдельно: в них другой код,
профилирование стадий отсутствовало, а конфигурации индексных структур
могли отличаться.

**Ограничение ресурсов:** 5 млн строк может требовать нескольких гигабайт
памяти и временного диска. Большой прогон проводить только при достаточном
свободном пространстве. Не коммитить raw результаты без явного запроса.


## Предварительная диагностическая проверка (не для статьи)

Запуск `20261029T014246117Z-c294a1d3-reopen-only`, 5 000 строк,
0 warmup + **2 измерения**, Linux поверх Windows, dirty worktree,
неполная публикационная конфигурация. Медианы в миллисекундах:

| Компонент Polar.DB | Конструктор (`constructor-open-only`) | Конструктор (`query-ready`) | `Refresh` |
|---|---:|---:|---:|
| Последовательность + primary | 7,17 | 9,39 | primary: 6,58 |
| External Int32 | 2,80 | 3,02 | 7,87 |
| External Int64 | 2,88 | 2,90 | 8,50 |
| External Guid | 4,42 | 3,45 | 11,20 |
| External String | **1051,51** | **901,70** | **845,43** |

Общие медианы Polar.DB: constructor-open-only **1097,97 мс**,
query-ready **1835,75 мс**. Это **не** доверительные интервалы и не
доказательство аналогичной пропорции на 5 млн строк.

Код `ExternalKeyIndex<string>` использует переменную длину
(`PTypeEnumeration.sstring`). При конструировании
`UniversalSequenceBase.OpenIndexSequence` открывается без отдельного
checkpoint, и может вызывать `RecoverFromExistingStream`.
При `Refresh` вызываются `_keys.Refresh()` и чтение всего snapshot.
Таким образом, переменно-размерный индекс — обоснованная гипотеза
причины больших времен, но доли восстановления границ записей,
десериализации и файлового ввода пока **не измерены отдельно**.
Полные большие прогоны завершились по лимиту 55 и 150 секунд;
никакие неполные серии не используются для научных выводов.

# Независимые повторения и неопределённость сравнения Polar.DB / SQLite

Этот протокол введён после рецензионного замечания № 4 к
[`POLAR_DB_ARTICLE_DRAFT.md`](POLAR_DB_ARTICLE_DRAFT.md). Историческая серия
`linux-wsl2-ext4-20261010` **не удовлетворяет** требованиям ниже:
много запросов или повторов в одном процессе — не много независимых экспериментов.
Старые медианы сохраняются как описательная статистика, а не как
статистически подтверждённые преимущества.

## Единица независимого измерения

Один независимый *повтор* — один завершённый запуск coordinator
`BenchmarkExecution`, который последовательно запускает по одному новому
дочернему процессу SQLite и Polar.DB. Внутри каждого процесса остаются
warmup, batch samples и отдельные запросы. Эти вложенные наблюдения
**не считаются независимыми репликациями**: они зависят от общего JIT, GC,
индексов, файлового кэша и машины.

Для каждого повтора и каждой комбинации
`(row count, phase, metric)` аналитический скрипт вычисляет медиану
внутренних samples для каждого движка. Таким образом, получается одна
пара значений на один независимый запуск.

## Порядок, выборка и воспроизводимость

- Минимум 8 завершённых запусков, в блоках по 4; для публикационной серии
  **заранее выбираются 12 или более**, кратно четырём.
- В каждом блоке порядок движков `SQLite→Polar / Polar→SQLite /
  Polar→SQLite / SQLite→Polar` (ABBA). Порядок фиксируется через
  `POLAR_BENCH_ENGINE_ORDER`, а не через чётность случайного run id.
- Каждый запуск имеет уникальный `POLAR_BENCH_RUN_ID`, собственные
  дочерние процессы, файлы и неизменяемый `combined.raw.json`.
- Совпадают commit, размеры набора, эксперимент, версия .NET/SQLite,
  модель GC, CPU/OS и Release. Незавершённые и dirty запуски не входят
  в анализ. Остановить серию при первой ошибке или таймауте.
- Зафиксировать заранее **основную метрику** и количество повторов.
  Разбор множества фаз и метрик — разведочный; учитывать проблему
  множественных сравнений, не выбирать единственную «победившую» постфактум.

## Оценивание

Для повтора `r` берутся медианы `t_SQLite,r` и `t_Polar,r`.
Анализируется `d_r = ln(t_SQLite,r / t_Polar,r)`. Центральная оценка —
`exp(median(d_r))`. Она >1, если наблюдаемое отношение на стороне Polar.DB.
95%-й **процентильный bootstrap-интервал** рассчитывается повторной
выборкой **целых пар запусков**, а не запросов из одного запуска
(10 000 resamples, фиксированный seed). Вместе с результатом выводятся
число независимых запусков и медианы времени каждой системы.

Интервал — оценка неопределённости при предположении сопоставимости и
достаточной независимости запусков, **не** доказательство причинного
эффекта и не замена отдельной проверки конфигураций. При охвате 1
направление различий нельзя считать убедительным; при малом числе повторов
bootstrap может быть неустойчив. Значимость, p-value и power-analysis
для исторических таблиц не заявляются.

ABBA снижает эффект систематического порядка движков, но не устраняет
drift частоты CPU, состояние SSD/page cache, общий swap, GC, внешнюю
нагрузку или корреляции соседних запусков. Для cold-cache результатов
нужен отдельный протокол управления кэшем, а не фраза «без разогрева».

## Команды

Из корня репозитория, после подтверждения достаточного диска/RAM:

```bash
python benchmarks/scripts/run-independent-series.py PkIntLookup --rows 50000 --repeats 12
python benchmarks/scripts/analyze-independent-series.py benchmarks/results/independent/<series-id>.json --output benchmarks/results/independent/<series-id>.csv
python -m unittest discover -s benchmarks/scripts -p 'test_independent_series.py'
```

Первый скрипт выполняет Release build и 12 **последовательных** завершённых
coordinator runs, контролирует порядок и записывает series manifest после
каждого успешного повтора. Исходные JSON/CSV сохраняются обычным стендом
в `benchmarks/results/raw/<experiment>/<run-id>/`. Второй скрипт
проверяет парность, окружение, число запусков и возвращает таблицу
`medianPairedRatioSqliteOverPolar` и `bootstrap95Low/High`.

Вновь полученные цифры не следует смешивать с сериями другого commit,
раскладки Guid, профиля индексов или состава операций.

## Необычные наблюдения

Историческая медиана volatile append при 50 тыс. записях (около
0,1169 мс) примерно на порядок выше медианы при 5 млн (около
0,0101 мс). Это **аномалия, требующая исследования**, а не
доказательство ускорения по мере роста данных. Нужно проверить порядок
итераций, распределение внутрисерийных samples, прогрев, пересоздание
индексов и влияние ресурсных пауз в независимых сериях. Не удалять
«неудобные» выбросы без заранее заданного критерия и отчёта об исключении.

Окончательные сравнительные выводы по производительности откладываются
до повторного измерения с исправленными индексными профилями
([`INDEX_PROFILE_PARITY.md`](INDEX_PROFILE_PARITY.md)) и достаточной
репликацией.

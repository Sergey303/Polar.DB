# Протокол прямого сравнения внешних индексов: апрель 2021 → ноябрь 2026

**Статус: закреплён после первого пробного запуска; до основной серии трёх парных блоков.** Пробные результаты не подменяют основную серию, не используются для изменения условий эксперимента или исключения результатов. Выполняется **одна задача** — успешный поиск по уникальному внешнему ключу `int`, без коллизий, версий и удалений.

## Идентичность источников

- Старый индекс: `agmarchuk/PolarDB@39cefe13db8697cf5f8e15edaa4677ba52a2cdea`, `IndexKey32Comp.GetAllByKey(int)`; вызывается с `comp=null`, поэтому историческая `Scale` включена. Сохранены её построение и дополнительные издержки в исходном алгоритме.
- Новый индекс: `Sergey303/Polar.DB@09ec0703f476f25ec79baff338843df8a8e83b35`, `ExternalKeyIndex<int>.GetManyByValue(int)` с `IComparer<int>.Default`.
- Из исходников каждого снимка собирается собственный `Polar.DB.dll`; общие `Program.cs` и `IndexAdapter.cs` создают данные, запросы, измерение и проверку. `LegacyAdapter.cs`/`ModernAdapter.cs` выполняют лишь API-специфические операции.
- **Исходники библиотек не модифицируются:** для исторического проекта в временной копии изменяется только `<TargetFramework>` (`netstandard2.0` → `net10.0`), для современного проекта при сборке задаётся `TargetFrameworks=net10.0`. Таким образом устраняется различие runtime, но не воспроизводится аппаратная среда 2021 года.
- Подготовленные SHA-256 исходников стенда: `Program.cs` — `47fadfaf9d8650a6611f986e9407761d67111d5a48cb23e93731f699f7807a72`; `LegacyAdapter.cs` — `2da7435d4f4af374a3d23ab3662a7db98e719dbf3e1059d35762df070747a454`; `ModernAdapter.cs` — `7e0733560fcea23129f79a1884b768fef00f8443153a0b5876c9b4132f839c23`; скрипт — `df33124f9bc5ebe247067661ab6fcac6ca712c94f96e004b433901496b8b85e1`.

## Общая логическая операция

- Одни и те же сериализованные поля: `(id:int, external_key:int)`; `id` возрастает от 0 до N-1, `external_key=N-1-id`. Идентичная логическая нагрузка, уникальный ключ, один результат на существующее значение.
- Размеры: **N=50 000 и N=1 000 000**. Поиск: **1000** случайно выбранных **существующих** ключей на размер; `Random(777)`. Для каждого запроса проверяется ровно одна строка, оба её поля и общая сумма `id`; отдельно проверяются отсутствие отрицательного ключа и крайние значения.
- Замеряем в миллисекундах `load_ms` (заполнение исходной последовательности); `prerequisite_ms` (2021: создание внешнего индекса; 2026: обязательное построение **первичного** индекса плюс создание внешнего); `index_build_ms` (внешний `Build()` + `Flush()`); `lookup_ms` (1000 запросов с проверкой результата). Обе версии имеют различный путь подготовки и файл-профиль: сравнивать только **операционный результат**, не объявлять одинаковую физическую работу.
- **Особенность реализации:** 2021 `BearingPure.Load` автоматически вызывает `Build` при пустом списке индексов; внешний индекс добавляется только позже. 2026 `USequence.Scan` для внешнего индекса требует предварительно построенного `UKeyIndex`, потому эта стоимость вынесена в `prerequisite_ms`. Исторический `IndexKey32Comp.Build` включает `GC.Collect()` и `Scale.Load`; современный внешний индекс держит оба массива (`T[]`, `long[]`) в ОЗУ после построения. Это влияет на интерпретацию абсолютного времени.

## Повторы, правила принятия, остановка

- Основная серия: **три парных блока** для каждого N, порядок **2021→2026, 2026→2021, 2021→2026**. Каждый процесс заново создаёт БД. Не выбираем лучшую попытку, не удаляем медленные измерения; приводим три значения, медиану и разброс, без доверительных интервалов и статистических утверждений.
- При ошибке сборки, несовпадении полей/количества результатов/контрольной суммы или невозможности запускать из-за диска **остановить всю серию**, не заполняя недостающие строки. Всегда проверять минимум **2 ГиБ** свободного места на `D:` до каждого процесса, не удалять чужие данные; удаляются только текущие файлы данных, созданные скриптом внутри его уникального каталога. Пробные запуски не включаются в итоговые медианы.
- Среда первой пробы: Intel Core i5-12400, 12 логических CPU, WSL2 Linux 6.18.33.2, SDK 10.0.112, Runtime .NET 10.0.12, Release, один физический хост. Реальные параметры основной серии подтвердить из логов.
- Команда: `benchmarks/scripts/run-index-evolution-direct.sh 3`. После завершения публикуются компактная таблица **всех** результатов, манифест и методика; исходные многократные временные файлы БД не коммитятся.

## Границы научных выводов

Измерение корректно характеризует только **уникальный внешний `int`-ключ без изменений**. Результаты нельзя распространить на коллизии разных ключей у старого `GetAllByKey`, неуникальные внешние ключи, запросы по строкам/Guid, холодный кэш, сравнение жизненного цикла с транзакционными гарантиями или всю архитектуру Polar.DB. По 3 парам допустимо только **описательное** сравнение на одном оборудовании. Обязательная проверка первичного индекса новой версии делает полную стоимость подготовки систем неэквивалентной. Нельзя приписывать обнаруженную разницу в задержке исключительно алгоритму бинарного поиска: 2021 читает сериализованные пары через `UniversalSequenceBase` и `Scale`, 2026 ищет в массивах ОЗУ.

# Контролируемая резидентность файлов первичного индекса: серия 4B

Материал воспроизводимости к статье [«Экспериментальное исследование характеристик последовательностей и индексных построений библиотеки Polar.DB»](POLAR_DB_ARTICLE_DRAFT.md). Это **отдельный независимый эксперимент** над поиском по первичному ключу `int` на 20 млн строк; его результаты не объединяются с основной серией 4 ноября 2026 года на 50 тыс. и 5 млн строк.

## Постановка и реализация

`UKeyIndex.TryGetIndexedValueAndOffsetByKey` ищет хеш ключа в загруженном массиве `hkeys_arr`, затем получает адрес записи через `offsets.GetByIndex(pos)` и саму запись через `sequence.GetByOffset(candidateOffset)`. Соответствующие файлы: `f1.bin` — отсортированные хеши (80 000 008 байт), `f2.bin` — смещения (160 000 008 байт), `f0.bin` — записи (2 060 000 008 байт). В отдельном протоколе выясняется, как потеря файловых страниц влияет на время *одного и того же* поискового сценария.

В режиме `uniform-v4` все файлы подготовленной базы сначала отображаются через `mmap` и закрепляются в RAM вызовом `mlock` **до открытия движка и разогрева запросов**. Непосредственно перед измерением выбранный файл освобождается через `munlock`/`munmap`, после чего к нему применяется `POSIX_FADV_DONTNEED`. Остальные файлы остаются закреплёнными до конца измерения. Резидентность страниц проверяется `mincore` до воздействия, перед пакетом запросов и после него. Успешность `mlock` и объём закреплённых байтов проверяются отдельно. Такой режим создаёт искусственно контролируемые состояния кэша, а не имитирует обычную работу приложения.

Использованы **20 000 000** детерминированных записей, **500** запросов разогрева, **10 000** запросов для пакетного среднего и **2000** иных ключей для отдельной оценки задержек. Всего **12 500 уникальных ключей** без повторения; одинаковый зафиксированный поток ключей использовался в обеих системах и всех запусках. Все 400 диапазонов по 50 тыс. строк представлены в выборке. Нагрузка содержит успешные поиски; отсутствующие ключи и изменение данных не измерялись.

В каждом из **8 независимых блоков** выполнены шесть условий в заранее случайно заданном порядке с чередованием обратного порядка: Polar.DB с полной резидентностью; вытеснение только `f1.bin`, только `f2.bin` или только `f0.bin`; SQLite с полной резидентностью или вытеснением всего файла. Каждый запуск — отдельный контейнер с **8 ГиБ RAM, без swap**, лимит закрепления памяти **3 ГиБ**. Условие допуска к анализу, порядок и правило подтверждения зафиксированы **до серии**; незавершённые и отклонённые попытки должны учитываться без повторного подбора.

## Основной результат

Первичное сравнение — отношение **среднего времени поиска с вытесненными смещениями `f2.bin` к среднему времени поиска с вытесненным файлом хешей `f1.bin`** в рамках одного блока. Среднее по запуску вычисляется по 100 средним значениям пакетов по 100 запросов. Это не медиана индивидуальных задержек.

| Блок | Хеши `f1.bin` вытеснены, мкс/запрос | Смещения `f2.bin` вытеснены, мкс/запрос | Отношение `f2/f1` |
|---:|---:|---:|---:|

**Все 8 из 8 пар корректны.** Геометрическое среднее парных отношений — **23,6216**, двусторонний **95%-й процентильный bootstrap-интервал [20,8268; 26,3142]** (10 000 перевыборок блоков, фиксированное начальное значение генератора `20261108`). Во всех восьми парах время поиска с вытесненными смещениями больше. Заранее заданный критерий подтверждения — не менее шести корректных пар из восьми и нижняя граница интервала строго больше 1 — выполнен. Это подтверждение *эффекта выбранного вмешательства*, а не оценка произвольного сценария эксплуатации Polar.DB.

## Дополнительные наблюдения и ограничения

| Система и условие | Принято/выполнено | Среднее по 8 запускам, мкс/запрос | Чтение процесса за пакет, МБ (среднее) |
|---|---:|---:|---:|
| Polar.DB, все файлы закреплены | 8/8 | 11,793 | 0,000 |
| Polar.DB, вытеснен `f1.bin` | 8/8 | 9,017 | 0,002 |
| Polar.DB, вытеснен `f2.bin` | 8/8 | 210,689 | 93,250 |
| Polar.DB, вытеснен `f0.bin` | 8/8 | 230,837 | 81,142 |
| SQLite, файл закреплён | 8/8 | 19,167 | 0,001 |
| SQLite, файл вытеснен | 8/8 | 249,257 | 46,850 |

В серии выполнены и приняты все **48 из 48** заранее назначенных запусков; контрольные суммы запросов совпали с эталоном, порог `memory.max` не достигался, OOM и CPU throttling не зафиксированы. Дисковый файл хешей `f1.bin` почти не перечитывался, что согласуется с поиском по `hkeys_arr`. Вытеснение `f2.bin` вызывало около 93,25 МБ чтений процесса за измеренный пакет при резидентном `f0.bin`. **`read_bytes` — счётчик процесса, а не измерение физических чтений конкретного файла**. В отдельных опытах менялась резидентность одной страницы служебного файла `f0.state` (24 байта); протокол основного вмешательства требует сохранять резидентность `f0.bin`, `f1.bin`, `f2.bin`, а не этой служебной страницы.

Статистическая неопределённость рассчитана по **восьми блокам одного хоста**, а не по десяти тысячам коррелированных запросов. Использованы один набор данных, одна последовательность ключей и искусственное закрепление страниц. Полученные данные **не доказывают** универсального превосходства Polar.DB над SQLite, наличия порогового объёма RAM, точной атрибуции операций накопителя к файлам, поведения при отсутствии ключей либо переноса результата на другое оборудование.

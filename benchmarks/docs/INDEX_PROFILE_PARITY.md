# Сопоставимость индексных профилей Polar.DB и SQLite

Этот документ фиксирует конфигурацию **новых** измерений после замечаний к
`POLAR_DB_ARTICLE_DRAFT.md`. Нельзя сравнивать их напрямую с исторической серией
`linux-wsl2-ext4-20261010` и считать старые медианы результатами новой конфигурации.

## Проверяемый логический индексный профиль

| Сценарий | Polar.DB | SQLite |
|---|---|---|
| `PkIntLookup` | Первичный `int id` | `id INTEGER PRIMARY KEY` |
| `PkLong/Guid/StringLookup` | Первичный по выбранному полю | `UNIQUE INDEX` только по выбранному полю, `id` без PK |
| `External*Lookup` | Первичный `long id` + один внешний индекс | `id INTEGER PRIMARY KEY` + индекс только по выбранному внешнему полю |
| `AppendOnly`, `DeleteOnly`, `ReopenOnly` | Первичный `id` + четыре внешних индекса | `id INTEGER PRIMARY KEY` + четыре неуникальных индекса |
| `BuildExternalIndexesOnly` | Первичный уже подготовлен, далее строятся четыре внешних | PK уже подготовлен, далее строятся четыре внешних |

Реализации не обязаны использовать идентичные физические структуры (например,
SQLite rowid и хеш-массив Polar.DB), но должны обслуживать сопоставимые логические
ключи и индексы. Отличаются семантика физического удаления (`DELETE` против tombstone),
граница фиксации, модель кэша и расходы на восстановление; эти различия следует
явно учитывать при интерпретации эксперимента.

В `SqliteStore.IndexProfiles.cs` профиль выбирается по `ExperimentKind`.
После создания каждого набора данных профили **проверяются во время выполнения**
через `PRAGMA index_list('rows')` по точному набору имён индексов.
Необходимые индексные структуры для сценария остаются в SQLite, а лишние
уникальные индексы больше не создаются.

## Публикационный протокол

1. Выполнить новую серию на фиксированном commit, сохранив раздельные процессы,
   размеры данных, seed, порядок запусков, Release и проверки rows/checksum.
2. Проверить `PRAGMA index_list` и состав PK, записать фактическую конфигурацию
   SQLite (`journal_mode`, `synchronous`, версию библиотеки) в журнал опыта.
3. Зафиксировать raw JSON/CSV, manifest, commit и контрольные суммы артефактов.
4. Заменить старые сравнительные таблицы **только после** полного измерения.
   При изменении набора физических полей или алгоритма восстановления проводить
   независимые повторные серии и не смешивать измерения разных версий.

В основной исторической серии `AppendOnly`/`DeleteOnly` SQLite дополнительно
обслуживал индексы `long_key`, `guid_key`, `skey`; следовательно, старые
коэффициенты скорости mutation не являются свидетельством преимущества
при сравнимых индексных профилях.

Для короткой проверки SQLite-ветви можно запускать worker с
`--benchmark-engine=sqlite --benchmark-run-id=<unique-id> --rows=2200`,
используя CLI соответствующего benchmark executable. Проверка одного worker
не является ни полным сравнением двух движков, ни публикационной серией.

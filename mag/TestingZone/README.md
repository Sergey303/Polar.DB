# TestingZone — минимальная проверка src/Polar.DB

Набор **самопроверяющихся** экспериментов по плану тестирования минимальной работоспособности.
Ошибки приводят к сообщению `FAIL` и ненулевому коду выхода. Нормальные результаты —
`PASS` с количеством записей, контрольными суммами и временем. Генератор данных
детерминированный; результаты времени зависят от ОС, диска, .NET и прогрева JIT.

## Запуск

Нужен .NET SDK из `global.json` репозитория, либо совместимый локальный SDK,
если запускать собранную DLL. Сборка:

```powershell
dotnet build mag/TestingZone/TestingZone.csproj -c Release
```

В каталоге `mag/TestingZone/bin/Release/net10.0`:

```powershell
# Совместимый режим запуска: ДВА РАЗНЫХ ПРОЦЕССА
./TestingZone.exe 5000000 true
./TestingZone.exe 5000000 false

# Полный короткий цикл: открытие, сканирование, редактирование и индексы.
./TestingZone.exe --scenario all --phase cycle --count 2000 --optimise false
./TestingZone.exe --scenario all --phase cycle --count 2000 --optimise true

# Увеличенный объем, разные запуски с одними и теми же данными:
./TestingZone.exe --scenario indexed --phase load --count 10000 --dir C:\Home\data\PolarTesting --optimise false
./TestingZone.exe --scenario indexed --phase reopen --count 10000 --dir C:\Home\data\PolarTesting --optimise false
```

На Linux можно использовать `dotnet /path/to/TestingZone.dll` с теми же параметрами.
Параметры: `--scenario base|mutation|indexed|all`,
`--phase load|reopen|cycle`, `--count N`, `--dir PATH`,
`--optimise true|false`. Без аргументов: `all/cycle/2000/false`.

**Важно:** новая программа хранит свои файлы в `TestingZone-data` текущего
каталога, если `--dir` не указан. Она **не использует**
старый `C:\Home\data\getstarted` автоматически. Для `reopen` сначала
запустить `load` с теми же `count`, `dir`, `optimise` и сценарием.
При `load` пересоздаются **только собственные файлы** соответствующего
подкаталога сценария (`base`, `mutation`, `indexed-standard` или
`indexed-optimised`); чужие каталоги не удаляются. Файлы `f*.state`
предназначены для контрольных точек последовательностей и удаляются
одновременно с `f*.bin` при новой загрузке.
На `reopen` отсутствие данных считается ошибкой, а не пустой БД.

## Что именно проверяется

| Сценарий | Проверки |
|---|---|
| `base` | `UniversalSequenceBase` с записями переменной длины: `AppendElement`, `Flush`, быстрый конструктор после перезапуска, `ElementValues`, `Scan`, `GetElement`, логический конец, контрольная сумма. Время каждого сканирования и скорость в млн/с. |
| `mutation` | Фиксированная последовательность `int`, редактирование **на месте** по смещению через `SetElement`, `GetByIndex`, сохранение и повторное открытие. |
| `indexed` | `USequence` key-value: `Load`, `Build`, `GetByKey`, 10K выборок, `Scan`, `Refresh` и сохраненный `state.bin`. |
| Редактирование `indexed` | Append-only замена существующего ключа, логическое удаление пустой записью, новая запись; запросы до и после повторной сборки, затем после открытия другим процессом. Проверяются отсутствие устаревших значений и дубликатов. |
| Индексы `indexed` | `ExternalKeyIndex<int>` (внешний сортируемый ключ), `SVectorIndex` (много тегов), строковый `SVectorIndex` (поиск по префиксу `Like`), `UIndex` (пользовательский компаратор, `GetAllBySample`), `ESortIndex32` (старый внешний сортировочный индекс). |
| Конфигурации | `optimise=false/true` с **раздельными файлами данных**, два формата записей, самостоятельные `load` и `reopen`. |

При `--scenario all` исходная последовательность получает все `N`
записей, но индексированная часть ограничена `min(N, 25000)`, чтобы не
потребовать чрезмерной памяти. При явном `--scenario indexed` используется
точно заданное число записей (`N >= 20`).

## Два независимых файла состояния

Для файла данных `f0.bin` базовая последовательность сама поддерживает
`f0.state` (версия, `Count`, `AppendOffset`). `FileStream` обнаруживается
автоматически; для произвольного `Stream` можно явно указать путь третьим
аргументом конструктора `UniversalSequenceBase`. В `Flush()` данные
сохраняются раньше новой контрольной точки; публикация `.state` выполняется
через временный файл и атомарное переименование.

`USequence` отдельно поддерживает прежний `state.bin`: первые два поля
означают границу последнего индекса, далее записаны флаги и устаревшие
смещения. При наличии нового хвоста `USequence.Refresh()` восстанавливает
динамические ключи, а не считает всё уже проиндексированным.

При отсутствии/порче `f0.state` последовательность проверяет записи
и пересоздаёт контрольную точку. Для старых баз `USequence` может
использовать прежний `state.bin` как подсказку **только если** она
совпадает с заголовком и текущей длиной файла. В противном случае
выполняется полный проход. Повторный `Refresh()` базовой
последовательности сразу после конструктора **не требуется**; публичный
`Refresh()` сохраняет строгую проверку структуры файла.

Быстрая подсказка не проверяет байты каждой записи: изменения внутри
файла при неизменной длине могут требовать отдельного полного сканирования.
Механизм рассчитан на одного записывающего владельца, без параллельной
записи двумя экземплярами.

## Границы эксперимента

- `Like` означает **префиксный** поиск, а не произвольную SQL-подстроку.
- Редактирование записи переменного размера проверяется безопасной
  append-only версией с прежним первичным ключом. Изменять длину значения
  *на месте* через `SetElement` без контракта на занимаемые байты нельзя.
- `ExternalKeyIndex<int>` — внешний **ключевой** индекс; это не
  проверка дисковой merge-sort сортировки гигантских данных.
- Эксперимент проверяет функциональный минимум и скорость,
  но не заменяет полный набор тестов на повреждение файлов, отказ питания
  и сравнение производительности между версиями.

Файл `test3.cs` исходного эксперимента сохранен для сравнения;
новый `Program.cs` запускает воспроизводимые проверочные сценарии.
